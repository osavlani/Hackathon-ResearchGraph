# Frontend UX audit and redesign

*Scope: the presentation layer only. The graph data (`public/`), the analysis code (`src/analysis/`, `src/data/`, `src/types.ts`) and the gap engine's logic are untouched. The engine output was re-run and is byte-identical (see §6).*
*Crucible isn't implemented in this repository (it exists only as a proposal in `HACKATHON_ANALYSIS.md`), so it wasn't built or tested here.*

Screenshots are in `docs/ux/` (`before-*` and `after-*`).

## 1. Problems in the original UI

References are to the pre-redesign code at commit `438059c`.

### 1.4 Visual design and responsiveness
| # | Problem | Where |
|---|---|---|
| P13 | **Box-in-box styling:** every panel, card, chip and list item had a 1 px border, so there was no hierarchy. There was also a decorative gradient logo and a radial graph background. Base font was 13 px, with 10–10.5 px labels and badges. | `index.css:36, 44, 54, 82, 94` (old) |

- graph views are filtered, so all 1,630 nodes are never drawn at once.

## 2. Redesign

### 2.1 Layout before and after

**Before (desktop):** a single scrolling page.
```
┌ topbar: logo · 4 status pills ───────────────────────────────────────┐
├ Search + corpus (290px) ┬ toolbar (4 rows) + graph ┬ Inspector (360px, always) ┤
├ Research discovery: 5 columns of cards ───────────────────────────────┤
└ Knowledge gaps: 60-row table with inline notes ───────────────────────┘
```

**After (desktop, ≥1280 px):** a fixed one-screen app with no page scroll.
```
┌ ResearchGraph · purpose line │      [ Search a topic…  (Search) ]      │ 30 papers · 1,630 entities · 60 gaps ┐
├ [Papers|Gaps|Discover] ┬ ‹ ⌂ Topic: alignment faking   [Find on graph][Filters][Legend] ┬ Details & evidence  ✕ ┤
│ one list at a time      │                    GRAPH (primary)                     ＋ − ⤢ │ (only when something  │
│ (300px, scrolls)        │ 42 of 1,630 nodes shown ⓘ                                     │  is selected, 400px)  │
└─────────────────────────┴───────────────────────────────────────────────────────────────┴───────────────────────┘
```

- **1024 px:** same structure. The details panel floats over the right edge of the graph instead of taking a column.
- **390 px:** search bar, then a tab row (Graph · Papers · Gaps · Discover). One pane shows at a time. Details stack under a graph shortened to 40%, so the selected node stays visible.

### 2.2 Changes and the reasons for them

| Change | Fixes | Implementation |

Engine suggestions are labelled "Suggested by ResearchGraph… not a result", and "Suggested directions" cards have a dashed violet edge. | P12 | `ui.tsx` (`ClaimBadge`), `index.css` |

## 3. Functionality preserved

Every capability from the original UI is still reachable:

- topic search and paper ranking with "via" entities;
- matching-entity chips;
- the corpus list and the missing-paper warning;
- all five graph views, double-click focus and neighbourhood highlight;
- type filters, the findings toggle, the gaps toggle and "find in view";
- fit to screen;
- the legend, including verdict colours;
- edge evidence: claim type, negation, grounding, validation statuses, contexts, papers, derived-link notes, and unverified quotes kept in a collapsed section;
- gap details: type, score, title, verdict, note, corpus references (including "missing" papers), rule description, focus entities, every resolution with its observed/weaker basis and paper links, involved papers;
- paper details: aligned papers with shared entities, mention / mentioned-by with ambiguity flags, entities by type, gaps it touches;
- entity details: aliases, papers, gaps with verdicts, all incoming and outgoing claims, evidence;
- gap filtering by type and verdict;
- all five insight lists.

**Moved rather than removed:**

| What | Where it went |
|---|---|
| The gap table's score and "corpus fixes" columns | The gap details panel (score in "Why the rule flagged this"; fix count beside "How papers in the collection could close it") |
| Per-paper entity count in the corpus list | The paper details header |
| The source label pill | The tooltip on the stats line |

**Unchanged:** `public/graph.json`, `public/gap_verifications.json`, `src/analysis/*`, `src/data/*`, `src/types.ts`, `App.tsx`, `scripts/`.

The full run was repeated 4 times after the final changes.

## 6. Heuristic usability review

*This is an expert heuristic review by the implementer, using Nielsen's heuristics and the task questions in the brief. **It isn't user testing:** no real users were observed or surveyed, so nothing here says users prefer the redesign.*

| Question | Assessment |
|---|---|
| Can a new user find the primary workflow? | Likely. The top bar states the purpose, the search field is the dominant control and has an example, example topic chips sit on the left, and a 4-step card explains clicks. Risk: the overview graph is dense, so first-time users may still click randomly before searching. |
| Can someone find a relevant paper quickly? | Yes. One search gives ranked papers with a "Mentions …" reason, and the results stay available while you browse. |
| Can they reach source evidence without excessive navigation? | Improved. Node → details → "Claims involving it" → quotes is 2 clicks, with no hunting on the canvas. Quotes show paper, page and verification status. |
| Can they understand what a research gap means? | Improved. There's a tab intro (a lead to check, not a finding), a per-type definition, and a verdict definition with reviewer provenance. The engine's own titles still say "in the corpus" (engine copy, left unchanged on purpose). |
| Does the interface direct attention well? | Mostly. The graph dominates, and details appear only on demand. In dense views, labels still overlap (see §7). |
| Are advanced details available without overwhelming? | Yes. Extraction details, rule rationale, scores, approximate mention detection and unverified quotes are all one click away, collapsed. |
| Is the graph useful rather than decorative? | Partly. The focused views (paper, entity, gap, claim) are informative. The overview is mainly an entry point. Layouts are re-randomized whenever the view changes. |
| Does it feel cohesive and trustworthy? | The consistent tags, the visual difference between source quotes and UI text, explicit "suggestion" labelling and visible reviewer provenance support trust. Whether it *feels* trustworthy to researchers needs real users. |

## 7. Remaining usability issues

1. **The layout re-randomizes** (fcose `randomize: true`) whenever the view or a filter changes, so users lose their mental map. Positions should be cached per view.
2. **Label overlap** in dense views (overview: 110 nodes; large entity neighbourhoods). Labels could be shown only above a zoom threshold or for high-degree nodes.
3. **The canvas isn't keyboard-accessible.** Keyboard and screen-reader users must use the sidebar and details lists.
4. **The legend shows colours but not node shapes**, and node colours aren't checked for colour-blind distinguishability (shapes differ per type, which helps).
5. **The engine's titles use "corpus" while the UI says "collection",** a small inconsistency. It was left unchanged to avoid touching engine strings.
6. **No direct link to the PDF page** for a quote: there's no PDF hosting in the repo.
7. **Small inline text links** (paper and entity links in the details panel) are about 20 px tall on mobile, below the 24 px target-size guideline.
8. **Bundle size** is about 851 kB, mostly cytoscape. `GraphView` isn't lazy-loaded.
9. **The dev-only test hook** `window.__cy` is set only when `import.meta.env.DEV` is true and is stripped from production builds.

## 8. Recommended next improvements

1. **Stable layouts:** cache node positions per view hash, and animate between views instead of re-randomizing.
2. **Zoom-dependent labels** and a "highlight path" mode for the focused node.
3. **Integrate Crucible** (if built) as a "Stress-test this claim" action in the claim details panel, reusing `ClaimBadge`, `ShowMore` and the evidence list. No new panel needed.
4. **Keyboard navigation of the graph**, for example arrow keys moving between neighbours of the selected node, with an aria-live announcement.
5. **Lazy-load `GraphView`** with `React.lazy` to cut first-load JS.
6. **A short moderated test with 3–5 researchers** on the five workflows, measuring time to first evidence quote and gap comprehension, before drawing conclusions about usability.
